# Need auto-image sourcing

Rule: item **and** volunteer requests without an uploaded photo get an auto-sourced image, generated by AI only. Stock-photo search was removed (Aug 2026) after a keyword match returned a photo that misrepresented the requester. Uploaded photos always win; the guard lives in SQL (`recordGeneratedImage` only writes where image_url is null or image_generated), not in route code.

**Why:** stock search cannot constrain who or what appears in frame; a fixed generation prompt can. Uploaded-wins in SQL closes the async race between background sourcing and a staff upload. Per-image cost is immaterial at this volume.

**How to apply:**
- Both kinds share one service module with a per-kind DAL adapter. Add a kind by adding an adapter — never by copying the module, and never by hardcoding a table in the sweep job (a missed kind leaves those failures stuck forever).
- Any new write path that sets an uploaded image must also clear `image_generated`/`image_gen_status` so automation never touches it again.
- The guardrail prompt block is held fixed per kind, never varied per request. People **are** shown — a deliberate reversal of the "no people" default in the source guardrail doc, because in-use imagery drives donation intent. The never-show list (distress, rescue framing, charity iconography) stays intact, and the donated item never reads as worn or secondhand even while in use.
- Generation has no post-hoc verification, so the admin approval screen labels every `imageGenerated` row "AI-generated — review before approving."

Provider quirks:
- OpenAI `/v1/images/generations` REJECTS the old `response_format` parameter (`Unknown parameter`). Use `gpt-image-1`; it returns `b64_json` by default. Square 1024x1024 is a native generation size, not a crop.
- The user's OpenAI account has been at "Billing hard limit has been reached" since Aug 2026 — generation fails visibly until they add credit; this is account-side, not code. Tests must treat it as SKIPPED, not a code failure, while still asserting the failure landed on the row.
- Failures must land on the row (`image_gen_status='failed'` + message) so staff see them on the admin request panel; retry = staff Regenerate button or the sweep.

Casting and closeness rules (learned from reviewing real output, Aug 2026):
- Name the casting explicitly and rotate it from a stable hash of the request id. Prompt silence is not neutrality — the model returns one default person for every prompt, so unrelated requests come back with the same face. Hash-based rotation keeps it varied across requests but stable for one request, so Regenerate does not reshuffle a family. Draw a second, always-different descriptor for unrelated pairs (volunteer + person helped) so no fixed pairing settles in.
- Anti-charity rules need a carve-out for ordinary closeness. "No figure above / handing down to another" is about donor-and-recipient staging between strangers; read literally it also bans a parent leaning over their own crib. Same for "downcast gaze" — looking down at your own baby is tenderness. Scope both to shame/benefactor framing, and say the wholesome case is welcome.
- Preview prompts for free with the print-prompt script rather than spending a generation; render candidate prompts through the agent-side image generator to sanity-check guardrail wording before paying the provider.

Billing routes (Aug 2026): the app posts to OpenAI directly with the user's own key, so provider limits are account-side. Replit AI Integrations can supply OpenAI/Anthropic/Gemini/OpenRouter credentials with Replit-managed billing at public API prices (paid plan; covers gpt-image-1 and gpt-image-2), but it is not exposed as a connector in searchIntegrations and no managed credential is injected until it is enabled.
