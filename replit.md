## What this is

A marketplace connecting member organizations' material and volunteer needs to the public's willingness to meet them. Organizations post needs. The public claims items or expresses interest in roles. Staff approve organizations, members, and requests before anything reaches the public.

Node, TypeScript, deployed here, mirrored to GitHub.

## Stack

**Database:** Replit-managed Postgres (Helium). Standard `pg` driver only, never a Neon-specific client, so a future move stays optional rather than required (D58).

This system is live and in use. Data loss is unacceptable. Silent failure is worse than loud failure. Data loss is unacceptable. Silent failure is worse than loud failure.

## Rules that are never broken

1. **No text-matching joins.** A person resolves to an organization through `org_memberships` and nothing else. A query comparing a name string to associate records is wrong.
2. **`quantity_claimed` and `quantity_interested` are written by `record_item_pledge()` and `record_volunteer_signup()` only.** No other code path updates them. If you are writing `update items set quantity_claimed`, stop and call the function.
3. **`quantity_remaining` is generated.** Never written.
4. **Every status transition writes an `approval_events` row** in the same transaction as the status change.
5. **Every email send writes an `email_log` row** before dispatch, updated on result.
6. **`legacy_wix_id` is never a foreign key.** Import reconciliation and legacy redirects only. Application logic joins on `id`.
7. **Deletion is not a workflow.** Members are removed by status. Requests are archived. Nothing in the member portal or public flows issues a DELETE.
8. **Authorization is server-side, on every request, before the query.** Never derive it from a URL parameter, a client-supplied org id, or a hidden form field.
9. **No secrets in the repo.** Environment variables, including in comments and test fixtures.
10. **The people served by these needs are never named in this system.** No recipient table, no beneficiary record. Do not add one.
11. **A person is identified by email, never by name.** Two name inputs, two columns, stored as entered. Never concatenate them into one string. Never split one string into two. This holds on public forms, portal forms, admin forms, and the migration.

## How to build a surface

One surface per task. Read its spec and both screenshots first. A surface with no spec and no screenshots does not get built.

Match the screenshots on: pages and their order, fields and their sequence, label text, button placement and labels, message text, conditional show and hide and enable and disable behavior, empty states.

Approximate: pixel spacing, font rendering, minor color variance.

Desktop and mobile are separate layouts and may differ substantially. Build both. Mobile is not a scaled-down desktop.

**Verbatim copy is verbatim.** Do not improve it, shorten it, or make it consistent across surfaces. If two surfaces say different things, they say different things.

## `[CAPTURE]` means stop

A `[CAPTURE]` marker in a spec is a value nobody has recorded yet.

**Never invent one.** Do not write plausible copy, guess a label, or pick a reasonable default. Build what is specified around it, leave the marker visible in the code as a comment, and report it.

A spec with open captures is still buildable. A spec filled in with invented copy is not correctable, because nobody can tell afterward which values were real.

## Stop and ask

Do not resolve any of these in code:

- A task seems to need a feature not specified in `Handbook.md`
- A spec and this file disagree
- A spec and `schema.sql` disagree
- You need a table, column, or index that does not exist
- A `[CAPTURE]` blocks the work rather than sitting beside it
- The work would touch a counter column, delete a row, or add a public endpoint

## Do not build

Not this week, and do not add columns, routes, or UI in anticipation:

- Fulfillment tracking. No status on pledges, no receipt step, no confirmation flow
- Reporting or an impact dashboard. No aggregate metrics, no charts, no counts on any surface. When reporting is built, do not inherit the public filter `organizations.status = 'approved'` or disabled orgs vanish from annual counts (D44)
- The digest send job. The subscriber table and the subscribe form are in scope; the send is not. Thursday's demo does not send to the live list (D46). When the send job is built, a request is digest-eligible only when `approved_at` is both non-null and within the lookback window (D43). Historical migrated rows stay null; live approvals write `approved_at = now()` (D48)
- Public per-organization pages. Slugs exist; no route consumes them
- Anything not specified in `Handbook.md`

## Conventions

- TypeScript strict. No `any` in committed code.
- All database access through one data-access layer. No SQL in route handlers or components.
- Migrations are numbered and applied in filename order by `npm run db:apply-migrations`, which records each applied file in `schema_migrations` and only runs pending ones — safe to re-run on fresh and existing databases alike; applied files are immutable (a content change fails loudly). `0001` is the base schema; `0002` (captain-ordered) repairs the phone-match behavior in the pledge/signup functions. **Creating a new migration is not your call.** A schema change is a captain decision.
- Every mutation validates server-side. Client-side validation is a convenience, never a control.
- Timestamps stored UTC as `timestamptz`, rendered America/Los_Angeles.
- Database: snake_case, plural tables. TypeScript: camelCase values, PascalCase types. Routes: lowercase, hyphenated.
- No currency anywhere in this system. Do not add price fields.

## Foundation (built, Aug 16 2026)

The foundation task is done: schema applied and dumped, DAL, routes, auth, storage
adapter, seed. Surface tasks build on it; nothing here is renamed.

- **Run:** workflow "Start application" (`npm run dev`, port 5000). `npm run check`
  (strict tsc) must stay clean. `npm run db:seed` is idempotent and prints the staff
  logins. Database setup, fresh or catching up: `npm run db:apply-migrations`
  (applies pending `/migrations` files in order, tracked in `schema_migrations`),
  then `db:apply-auth-schema`, `db:apply-rls`, `db:seed`.
  `npm run db:dump-schema` regenerates `schema.sql` after any approved change.
- **Contract:** `docs/data-access.md` — DAL signatures, contexts/RLS, guards, email,
  storage, error codes. All final. `docs/build-log.md` — append your surface row.
- **Auth:** Better Auth magic-link only, mounted at `/api/auth/*`. `POST
  /api/login/magic-link` returns a uniform 200 regardless of registration status.
  Requires `POSTMARK_SERVER_TOKEN`; without it, sends log a failed `email_log` row and the
  server stays up. Seeded staff: `tiffany@defendingthecause.org` and
  `christina@defendingthecause.org` (staff_admin, real inboxes),
  `approver@thealliance.example.org` (staff_approver — synthetic, cannot receive
  mail). Postmark delivers only from verified sender signatures.
- **Dates over the wire are strings** — `date` → `YYYY-MM-DD`, `timestamptz` → ISO UTC
  (normalized in `server/db/client.ts`). Render America/Los_Angeles at the edge.
- **Fixed by `0002` (Aug 17 2026):** `record_item_pledge` / `record_volunteer_signup`
  no longer crash on a non-empty `phone`. A phone-only match always creates a new
  person with `needs_review = true` and a note naming every matched person; nothing
  is merged automatically (ADMIN-04). Details in `docs/data-access.md` §7.
- **Storage:** `server/storage/object-storage.ts` is the only object-storage path; a
  bucket must exist in App Storage before image upload surfaces work.
