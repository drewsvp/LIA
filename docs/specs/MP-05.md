## 1. Purpose

Where a member edits their organization's details and manages who else at the organization has access. This surface is now fully confirmed by capture, not inferred.

Organization fields mirror MP-03 section 5 (same population checklist per D61: ten values plus Other), pre-filled with the organization's current values. Submit button reads "Submit," not "Submit for Approval"; editing an already-approved organization doesn't re-enter the approval queue.

Below the organization fields and their Submit button, a "TEAM MEMBERS" section: one dropdown ("Click to see your team members." placeholder) and one "Remove User" button. This is the entire member-management portion of the surface, confirmed by capture, simpler than previously assumed, no per-row list with individual controls.

Primary contact fields on this surface show as a single "Name" field on the live site. Build as two per D41 regardless, same as every other form in the app.

## 2. Entry and exit

**Arrives from:** MP-04.
**Leaves to:** MP-04 via the back control.

## 3. Data

**Reads:** the session organization's editable fields (per MP-03 section 5), `org_memberships` for the session organization joined to `people` (first_name, last_name, email, phone) and `users` (status), `populations` (active rows, for the selector).
**Writes:** `organizations` and related tables on save; `org_memberships.status`, set to `removed`, on member removal.
**Functions called:** None.
**Never touches:** `people` on removal. Removing a member never deletes or modifies the person. It never touches `users` either; the account survives, the access does not.

## 4. Layout regions

Confirmed against MP-05-desktop.png, Aug 16 2026. One continuous page, in order:

1. **Page heading** and back control.
2. **Organization details region** ("ORGANIZATION INFO"). Editable organization fields per section 5, pre-filled, with Submit control.

## 6. Actions

**Submit**
- Enabled when: organization fields pass validation.
- Does: updates the session organization's editable fields per section 5.
- Transaction boundary: single update to `organizations` and related tables.
- Emails queued: none.
- On success: success message renders.
- On failure: failure message. Nothing changes.

**Remove User**
- Enabled when: a member is selected.
- Does: prompts for confirmation per section 8, then sets the selected `org_memberships.status` to `removed`.
- Transaction boundary: single update.
- Emails queued: none. Default: no email to the removed person. If the captain wants one, it is a new template and goes through `Handbook.md` section 13.
- On success: the success message renders, the selector refreshes without that member.
- On failure: the failure message renders, nothing changes.

Removal requires one confirmation click before it fires, matching standard practice for an action that revokes access. Correctable if the live surface shows single-click removal instead.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Organization details saved | Success message. Form retains values |
| Organization details save fails | Failure message. Nothing changes |
| No member selected | Remove User disabled |
| Member selected | Remove User enabled; activating it shows the confirmation prompt in section 8 |
| Removal confirmed | Membership set to `removed`; success message; selector refreshes |
| Removal fails | Failure message, no change |
| Organization has one active member | See section 12 |

## 9. Empty states

An organization with exactly one member, the owner who registered it, is the common case for a newly approved organization. The selector lists that person; Remove User is disabled when removing them would violate D6.

## 10. Mobile differences

Closed per D60. Single column, same regions in the same order, full-width controls.

## 11. Authorization

Verify the session user holds an active membership in the organization, server-side, before reading. Every membership read and the removal write are both filtered by the session organization.

**Any active member may remove another member (D5).** No owner-only restriction. Staff approval at ADMIN-03 is the control that makes open membership safe.

**A member cannot remove themselves (D6).** Prevent self-removal regardless of what the current surface allows; count it as a defect fix rather than a deviation.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Removal would leave the organization with zero active members | Blocked, with a stated reason. This locks the organization out and staff have to repair it manually |
| The selected member was already removed by someone else | Treat as a no-op success rather than an error. The intent is satisfied |
| Update fails | Failure message. Nothing changes |
| Removed member has an active session | Their next request fails the membership check at MP-02 and they lose access. Verify this |

## 13. Out of scope for this surface

- Inviting members. MP-06.
- Deleting a person or a user account. Removal is a status change. Invariant 7 in `Handbook.md` section 6.
- Approving a pending membership. ADMIN-03.
- Changing a member's role. Not built this week.

## 14. Acceptance

- Organization fields mirror MP-03 section 5 and pre-fill with current values.
- Submit saves without re-entering the approval queue.
- The selector lists only the session organization's active members.
- Removal sets `org_memberships.status` to `removed` and writes nothing to `people` or `users`.
- The removed person's `people` row still exists afterward, with their pledge and signup history intact.
- Removing the last active member is blocked.
- A member cannot remove themselves.
- A removed member with an open session loses access on their next request.
- Field order, labels, and messages match the desktop screenshot. Mobile matches the mobile screenshot.
