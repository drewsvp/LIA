## 1. Purpose

Where a member of the public reads a volunteer opportunity and expresses interest in specific roles. No login.

**This surface records interest, not commitment.** A person who checks a role is saying they want to hear more, and the organization follows up. That distinction runs through the whole surface: the counter is `quantity_interested`, the confirmation email sets an expectation of follow-up rather than thanking someone for a completed act, and the organization tracks who actually served in a separate column the public never touches.

Contact instructional copy states "1-3 business days," matching D52's `donor_volunteer_confirmation` follow-up window.

## 2. Entry and exit

**Arrives from:** PB-03, PB-00, direct links, and the legacy redirect `/area-needs-volunteer-request/:legacyId`.

**Leaves to:** confirmation on the same page. No redirect.

## 3. Data

**Reads:** `volunteer_requests` for `:id` where `status = 'active'`, `volunteer_roles` for that request, `organizations` (name, mission, website_url, logo_url, city, populations).

**Writes:** entirely through `record_volunteer_signup()`. The surface writes nothing directly. `email_log` rows for the two sends.

**Functions called:** `record_volunteer_signup(first_name, last_name, email, phone, request_id, notes, role_ids)`.

**Never touches:** `volunteer_roles.quantity_interested`, `quantity_remaining`, `quantity_confirmed`, or `volunteer_requests.status`.

`quantity_confirmed` deserves a specific note: it is the organization's private record of who actually served, edited at MP-12. Nothing public ever reads or writes it.

**Population display policy (D61):** The "Select 1-2" constraint is confirmed specific to MP-03's signup form only. Live organization profiles on this surface show anywhere from three to eleven populations selected. MP-05's edit checklist carries no cap; build it uncapped. Display only here, not selection.

## 4. Layout regions

Request detail (title, image, Volunteer Role Location, Volunteer Date, Details, Request Description), organization detail (boxed, below request detail, above roles), Volunteer Roles list, donor form, submit region. No agreement-checkbox region; this surface doesn't have one, unlike PB-02.

## 6. Actions

**Express Interest**
- Enabled when: at least one role is checked and required donor fields validate.
- Does: calls `record_volunteer_signup()` with the volunteer's details, the notes, and the checked role ids. The function resolves or creates the person, writes the signup and its role rows, and increments `quantity_interested` by one per role under a row lock.
- Transaction boundary: the entire function, one transaction.
- Emails queued: `donor_volunteer_confirmation` to the volunteer, and `org_new_volunteer` to the request contact.
- On success: confirmation per section 8.
- On failure: see section 12. Every entered value retained, including notes.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| A role's remaining is zero | That role's checkbox is disabled |
| Organization has no mission, website, or logo | Field hidden, not rendered blank. Deviation three |
| `deadline_type = 'date_specific'` | Volunteer Date displayed |
| `deadline_type` is any other value | Volunteer Date hidden or shows ongoing copy per capture |
| Request has no event location | Volunteer Role Location label and value hidden, not rendered blank. Same rule as deviation three for empty organization fields |

## 9. Empty states

An active request with no roles should not exist, since submission at MP-11 requires at least one. If reached, render the request detail with **"No volunteer roles are listed for this request yet."** rather than an empty roles region and a live submit.

## 10. Mobile differences

Closed per D60. Single column, same regions in the same order, full-width controls.

## 11. Authorization

None to view. The response must carry only the fields in section 3 and must not serialize the request's contact person, the organization's phone, or any existing signup data.

`:id` resolving to a non-active request returns the same response as a nonexistent one.

Public write endpoint: rate limited by IP with a per-endpoint ceiling (D10), server-side validated. Every role id is re-validated inside the function against a row lock regardless of what the client sent. The disabled checkbox is a courtesy, never a control.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| `role_full` raised | Transaction rolled back. Re-render availability, keep every entered value including notes, say which role filled |
| `request_not_active` raised | Tell the visitor the opportunity has closed and link back to PB-03 |
| `role_not_in_request` raised | Tampered payload. Generic failure, logged |
| No roles checked | Blocked with a message asking them to select at least one |
| Email dispatch fails after a successful signup | Signup stands. Logged as failed, surfaced in ADMIN-06. Volunteer sees success |
| A submitted email matches an existing person | Not an error. The person's name is updated to the values just submitted and the signup is attached to the existing row |
| A submitted phone matches a different existing person | Not an error and not a block. The new person is created and flagged for review. The supporter sees nothing unusual |

Losing typed notes on a failed submission is the specific thing to avoid.

## 13. Out of scope for this surface

- Any direct write to a counter column.
- Any login, account, or saved-volunteer behavior.
- Scheduling, shift selection, or calendar integration.
- Confirming a volunteer. That is the organization's action at MP-12.
- Withdrawing interest after submission. No path exists and none is added this week; the confirmation email carries the organization's contact details for exactly this.

## 14. Acceptance

- Request detail labels match section 5 verbatim, including Volunteer Date (not Deadline Type).
- Organization detail shows populations without a 1-2 cap (display only).
- Role rows use Select Role checkboxes, not quantity inputs.
- Notes field and helper text match section 8; notes reach MP-13 intact.
- Submit button reads Express Interest.
- A submission calls `record_volunteer_signup()` only.
- First and last name land in two separate columns per D41.
- A returning person with the same email creates no duplicate person, including someone who previously pledged an item.
- A single-word name in either field succeeds.
- A non-active `:id` is indistinguishable from a nonexistent one.
- Desktop and mobile match their screenshots.
