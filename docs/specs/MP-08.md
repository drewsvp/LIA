## 1. Purpose

The second step of creating an item request. A member who has just created a request adds the individual items it asks for, one at a time, then submits the completed request for staff approval. A request cannot be submitted with no items.

## 2. Entry and exit

**Arrives from:**
- MP-07, automatic redirect immediately after the request record is created. This is the normal path.
- MP-09, if the edit surface links back to add more items. No link exists; add-item functionality is inline on MP-09 per MP-09 section 2.
- Direct URL, for a member returning to a request left in `draft`.

**Leaves to:**
- MP-04 `/dashboard` on successful submit for approval.
- MP-04 `/dashboard` via the back control.

A member who navigates away without submitting leaves the request at `draft`. Draft requests are visible only to their own organization and appear nowhere public. Nothing is lost and nothing is orphaned.

## 3. Data

**Reads:** `item_requests` (title, description, image_url, deadline_type, deadline_date, status, org_id), `items` (all columns, for the added-items list), `organizations` (name, for display).

**Writes:** `items` on each add. `item_requests.status` and `item_requests.submitted_at` on submit. `approval_events` on submit. `email_log` on submit.

**Functions called:** None. The counter functions do not apply here; this surface creates items, it does not record pledges.

**Never touches:** `items.quantity_claimed`, `items.quantity_received`, `items.quantity_remaining`. New items are created with `quantity_claimed` and `quantity_received` at their column defaults of zero. `quantity_remaining` is generated and is never written under any circumstance.

## 4. Layout regions

1. **Request summary.** Read-only display of the request being built: title, description, and deadline date when applicable.
2. **Add item form.** Input fields for one item plus its add control.
3. **Added items list.** Every item currently on this request, appearing as each is added. Five columns: Item Name, Item Description, Quantity, Claimed Quantity, Item Condition.
4. **Submit region.** The Finish & Submit control.
5. **Back control.** Returns to the dashboard.

Confirmed against MP-08-desktop.png, Aug 16 2026.

## 5. Fields

Add item form:

| # | Label (verbatim) | Control | Required | Binds to | Validation |
|---|---|---|---|---|---|
| 1 | Item Name | Text input | Yes | `items.name` | Non-empty. Placeholder text: "Ex: Twin Bed, Size 2 Diapers, Double Stroller, Teen Bike, etc." |
| 2 | Item Descripton | Textarea | Yes | `items.description` | Label is misspelled on the live site, verbatim, keep it |
| 3 | Number of This Item Needed | Number input | Yes | `items.quantity_requested` | Integer greater than zero |

This surface collects the same fields MP-09 edits, not a subset. Description and condition are entered here, at creation, not deferred.

`sort_order` is assigned by the surface, not entered by the member. Each new item takes the next integer, so the list renders in the order the member added them.

## 6. Actions

**Add Item**
- Enabled when: all required fields pass validation.
- Does: inserts one `items` row against `:id` with the entered values, `quantity_claimed` and `quantity_received` at zero, and the next `sort_order`.
- Transaction boundary: single insert.
- Emails queued: none.
- On success: the item appears in the added items list, the form clears, and the success message in section 8 renders.
- On failure: the form retains its values and the error message in section 8 renders. Nothing is inserted.

The instructional copy above the form calls the button "Add Another Item," a real mismatch between that copy and the actual button label. Preserve both exactly as captured rather than reconciling them.

**Finish & Submit**
- Enabled when: the request has at least one item. Disabled otherwise, from first render. Disabled state visually confirmed in the capture, matching the existing zero-items gate.
- Does: in one transaction, sets `item_requests.status` to `pending`, sets `submitted_at`, and writes an `approval_events` row with `from_status = 'draft'`, `to_status = 'pending'`, and the acting user.
- Emails queued: `staff_new_item_request` to both staff addresses, and `org_request_received` to the submitting member. Queued inside the transaction, dispatched after the response.
- On success: redirect to `/dashboard`.
- On failure: the surface stays put, the request remains at `draft`, and the failure is shown. No partial submission.

The instructional copy calls this button "Submit for Approval." Preserve both labels exactly as captured rather than reconciling them.

**Back control**
- Enabled when: always.
- Does: navigates to `/dashboard`. No write.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Request has zero items | Finish & Submit is disabled |
| Request has one or more items | Finish & Submit is enabled |
| `deadline_type = 'date_specific'` | Deadline date is displayed in the request summary |
| `deadline_type` is any other value | Deadline date is hidden, not rendered blank |
| Item successfully added | Success message renders, form clears |

The deadline display rule is the read-only counterpart of the deadline control described in `Handbook.md` section 11. The control itself does not appear on this surface.

## 9. Empty states

The added items list renders an empty-state message before the first item is added: "No items added yet."

This surface is reached with an empty list every time it is used normally, so its empty state is the first thing every member sees here. It is not an edge case.

## 10. Mobile differences

Closed per D60. Single column, same regions in the same order, full-width controls.

## 11. Authorization

Before any read or write, resolve the session user's active `org_memberships` and confirm one of them matches `item_requests.org_id` for `:id`. The organization is never taken from the URL or a form field; `:id` identifies the request, and the request's own `org_id` is what gets checked against the session.

A member of a different organization gets the same response as a request that does not exist. Do not distinguish between the two; distinguishing them confirms the existence of another organization's records.

An unauthenticated visitor is redirected to `/login`.

A request whose status is not `draft`: the surface loads read-only with the submit control absent.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Item insert fails | Error message, form values retained, nothing written |
| Submit transaction fails at any step | Request stays at `draft`, no approval event, no emails queued, failure shown to the member |
| Email dispatch fails after a successful submit | The submit stands. The failure is recorded in `email_log` with status `failed` and surfaces in ADMIN-06. The member is not shown an error, because their action succeeded |
| `:id` does not resolve | Same response as an unauthorized request, per section 11 |

The distinction in row three matters and is easy to get backwards. The submit and the queue write are in the transaction; the dispatch is not. A dispatch failure is an operations problem, not a member-facing one.

## 13. Out of scope for this surface

- Editing or deleting an item after it is added. That is MP-09.
- Any write to a quantity column other than `quantity_requested`.
- Approving the request. Only staff do that, at ADMIN-02.

## 14. Acceptance

- The surface renders the correct request's title, description, and image.
- Deadline date is visible for a date-specific request and hidden for every other deadline type.
- Finish & Submit is disabled on arrival with zero items and enabled the moment the first item is added.
- Adding an item creates exactly one `items` row with all five field values, `quantity_claimed` and `quantity_received` at zero.
- Added items render in the order they were added.
- Submitting sets status to `pending`, writes exactly one `approval_events` row, and queues exactly two email types.
- Submitting redirects to `/dashboard`.
- A member of another organization cannot load the surface and cannot tell whether the request exists.
- Field order, labels, and every message match the desktop screenshot.
- Mobile matches the mobile screenshot.
