## 1. Purpose

Where a member of the public reads an item need and commits to donating specific items in specific quantities. No login. This is the surface the entire system exists to produce, and the one most sensitive to friction: every additional field, confusing label, or unexplained failure here is a need that does not get met.

It is also the only public surface that writes to counters, which means it is the only public surface with a real concurrency path.

## 2. Entry and exit

**Arrives from:** PB-01, direct links in email and social posts, and the legacy redirect `/area-needs-request/:legacyId`.

**Leaves to:** confirmation on the same page. Success copy in section 8.

## 3. Data

**Reads:** `item_requests` for `:id` where `status = 'active'`, `items` for that request, `organizations` (name, mission, website_url, logo_url, city, populations).

**Writes:** entirely through `record_item_pledge()`. The surface itself writes nothing directly. `email_log` rows for the two sends.

**Functions called:** `record_item_pledge(first_name, last_name, email, phone, request_id, notes, lines)`.

**Never touches:** `items.quantity_claimed`, `items.quantity_remaining`, `item_requests.status`. All three are the function's business. Invariant 2 in `Handbook.md` section 6 has no exceptions and this is the surface where it would be most tempting to make one.

## 6. Actions

**Claim Item(s)**
- Enabled when: at least one quantity is above zero, the agreement checkbox is checked, and the donor fields validate.
- Does: calls `record_item_pledge()` with the donor details and the non-zero lines. The function resolves or creates the person, writes the pledge and its lines, increments claimed under a row lock, and archives the request if every item reaches zero remaining.
- Transaction boundary: the entire function, one transaction. Person, pledge, lines, counters, and any resulting archive succeed together or none do.
- Emails queued: `donor_item_confirmation` to the donor, including the organization's contact information so they can follow up directly, and `org_new_item_donation` to the request contact.
- On success: the confirmation in section 8.
- On failure: see section 12. Every entered value is retained.

**Product link**
- Opens the item's `product_url` in a new tab. Standard practice for an external e-commerce link.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| An item's remaining is zero | That item's quantity input is disabled. No additional visual treatment beyond the disabled control |
| An item has no `product_url` | The link element is not rendered. Not rendered empty, not rendered disabled |
| Organization has no mission, website, or logo | That field is hidden rather than rendered blank. This is deviation three |
| `deadline_type = 'date_specific'` | Deadline date displayed |
| `deadline_type` is any other value | Deadline date hidden |
| Request has no dropoff location | **Confirmed: does not hide.** The captured example has no dropoff location and the label "Item Dropoff Location:" still renders with nothing after it. Build to match: render the label, leave the value blank when null. |

## 9. Empty states

An active request with no items should not exist, since submission at MP-08 requires at least one. If one is reached, render the request detail with a stated message rather than an empty items region and a live submit button.

## 10. Mobile differences

Closed per D60. Single column, same fields in the same order, full-width controls.

## 11. Authorization

None to view. The surface must return only the fields in section 3 and must not serialize the request's contact person, the organization's phone, or any supporter data into the response.

`:id` resolving to a request that is not `active` returns the same response as a request that does not exist. A pending request is not yet public and its existence is not disclosed.

This is a public write endpoint. It is rate limited by IP with a per-endpoint ceiling (D10). Every quantity is re-validated inside `record_item_pledge()` against a row lock regardless of what the client sent; the disabled input is a courtesy, never a control.

## 12. Error paths

This section is the substance of the surface. Handle every row.

| Failure | Rendered result |
|---|---|
| `insufficient_quantity` raised: another donor claimed the item while this visitor was filling out the form | The entire transaction rolled back, so nothing was recorded. Re-render current availability, keep every value the visitor entered, and tell them plainly which item was claimed and how many remain. Never a generic error, and never a silent partial success |
| `request_not_active` raised: the request was archived or fulfilled mid-form | Tell the visitor the need has been met, and link back to PB-01. This is good news badly timed and should not read as a failure |
| `item_not_in_request` raised | A tampered or stale payload. Generic failure, logged |
| Zero quantities submitted | Blocked at the surface with a message asking for at least one item |
| A quantity above an item's remaining submitted | Blocked at the surface, and rejected again by the function if it gets through |
| Email dispatch fails after a successful pledge | The pledge stands. Logged as failed in `email_log`, surfaced in ADMIN-06. The donor sees success because their pledge succeeded, and the organization can still see the pledge at MP-13 whether or not the email arrived |
| A submitted email matches an existing person | Not an error. The person's name is updated to the values just submitted and the pledge is attached to the existing row |
| A submitted phone matches a different existing person | Not an error and not a block. The new person is created and flagged for review. The supporter sees nothing unusual |
| Request fully claimed by this submission | Not an error. The function archives it. The donor gets the normal confirmation |

The first row is the important one. A busy request with a single remaining item will produce this collision, and the failure mode to avoid is a visitor who fills out the form, gets a red error, and leaves believing they donated. Tell them what happened, keep their details in the form, and show them what is still available.

## 13. Out of scope for this surface

- Any direct write to a quantity column.
- Any login, account creation, or saved-donor behavior.
- Marking a pledge fulfilled or received. Phase two.
- Storing the agreement consent.
- Editing or cancelling a pledge after submission. There is no path for this and none should be added this week; a donor who needs to cancel contacts the organization, which is why the confirmation email carries their contact details.

## 14. Acceptance

- The surface renders the correct organization's mission, website, logo, and city, resolved through `org_id`. Spot-check several requests against the organizations that own them; this is the visible proof that the mission-field fault is gone.
- An organization field with no value is hidden, not rendered blank.
- The product link renders as visible URL text with standard hyperlink styling when `product_url` is present, not as a separate button.
- The agreement checkbox renders checked on load.
- An item at zero remaining has a disabled quantity input.
- A submission calls `record_item_pledge()` and no code path on this surface updates a quantity column directly.
- Two simultaneous claims on the last remaining unit produce one success and one handled `insufficient_quantity`, with no counter drift. Test this deliberately.
- After a failed claim, the visitor's entered details are still in the form.
- A submission that claims the final remaining item archives the request with `archived_reason = 'fulfilled'`.
- Both emails send with resolved names and the organization's contact details present in the donor confirmation.
- A returning donor with the same email creates no duplicate person.
- First and last name land in two separate columns, never concatenated.
- A single-word name in either field succeeds.
- A non-active `:id` is indistinguishable from a nonexistent one.
- The response payload carries no contact or supporter data.
- Desktop and mobile match their screenshots.
