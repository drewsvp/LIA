## 1. Purpose

Where a member changes an existing volunteer request and the roles on it. Structurally parallel to MP-09.

**This surface is three independently-submitted forms on one page, not one form**, matching MP-09's pattern and its own instructional copy ("Use each part of the form separately"). Request-info fields, the roles list, and the add-role form each have their own submit action.

The same two deviations apply here: interested counts are display only (D1, deviation six) and the status selector never offers `active` to a member (D2, deviation seven).

## 2. Entry and exit

**Arrives from:** MP-04, by selecting a volunteer request and activating its edit control.
**Leaves to:** MP-04 via the back control.

Roles are added inline on this surface via the "ADD A NEW ROLE TO THIS REQUEST" form (region 4). No separate link to MP-11 exists and none is needed — add-role functionality is native to this page.

## 3. Data

**Reads:** `volunteer_requests` for `:id`, `volunteer_roles` for that request, `organizations.name`.

**Writes:** `volunteer_requests` request-level fields. `volunteer_roles` editable fields, and new rows. `approval_events`, when and only when status changes.

**Functions called:** None.

**Never touches:** `volunteer_roles.quantity_interested`, per the conflict below. `quantity_remaining`, which is generated. `approved_at`, `approved_by`.

## 4. Layout regions

1. **Heading.**
2. **Request-level fields.** Status, deadline, title, description, details, event location, people helped, and contact. All editable here except contact resolves by email policy on save.
3. **Roles list.** Every role, each with editable fields.
4. **Add role form.**
5. **Save region.**
6. **Message region.**
7. **Back control.**

Confirmed order: page banner and instructional copy, request-info section, roles list, add-role form, back control (top left).

### Add role form (inline)

Matches MP-11 section 5 exactly, including the "Role Descripton" typo. Same component reused. Writes immediately on its own submit action.

### Conflict 1: interested count must not be editable

`quantity_interested` is written by `record_volunteer_signup()` and by nothing else, per `Handbook.md` invariant 2. It is the counter that gates the public checkbox at PB-04, and an editable value desynchronizes it from the signup rows that back it.

**Specified behavior: interested is display only (D1).** `quantity_confirmed` remains fully editable, because that is the organization's record of who actually showed up and it is not a counter. Same deviation as MP-09's, settled in `Handbook.md` section 4.2, deviation six.

The distinction between interested and confirmed matters more on this surface than anywhere else in the portal, because they sit next to each other and mean different things. Interested is what the public expressed. Confirmed is what the organization observed. Column headers Role Name, Role Description, and Quantity match MP-11 exactly, confirmed from capture.

### Conflict 2: reducing needed below interested

Lowering `quantity_needed` below the existing `quantity_interested` produces a role with more interested volunteers than spots. `quantity_remaining` floors at zero so it will not go negative, but the state is wrong.

**Specified behavior:** block the save with a message naming the role and its interested count. Exact wording written fresh at build time.

## 6. Actions

Three independent submit actions, one per form region. Saving one region does not require saving the others.

**Submit Request Edits** (request-info region)
- Enabled when: request-info fields pass validation.
- Does: saves request-level fields only. Writes an `approval_events` row if and only if status changed.
- Transaction boundary: request-level fields only.
- Emails queued: submission emails when status moves to `pending`.
- On success: success message for this region.
- On failure: failure message, nothing written for this region, values retained.

**Submit Role Edits** (roles-list region)
- Enabled when: at least one role is present and role fields pass validation.
- Does: saves every role's editable fields in one transaction.
- Transaction boundary: all role changes succeed together or none do.
- Emails queued: none.
- On success: success message, list re-renders with recomputed remaining.
- On failure: failure message, nothing written, every entered value retained.

**Add This Role** (inline form, per MP-11)
- Enabled when: the add form passes validation.
- Does: inserts one `volunteer_roles` row with interested and confirmed at zero and the next `sort_order`. Writes immediately on submit.
- Transaction boundary: single insert.
- Emails queued: none.
- On success: role appears in the list, form clears.
- On failure: form retains values, error renders, nothing inserted.

**Back control**
- Navigates to MP-04. No write.

### Conflict 3: the status selector

Identical to MP-09's. A member may move a request `draft` to `pending`, `active` to `archived` with `archived_reason = 'manual'`, and `archived` to `pending`. A member may never set `active`; that option does not render for a member. Approval is ADMIN-02's, staff only.

Status option labels are contextual on current status, inferred from D2 (same logic as MP-09):

| Current status | Options offered to member |
|---|---|
| `draft` | Pending (submit for approval) |
| `active` | Archived |
| `archived` | Pending (reopen for re-approval) |

`active` is never offered directly; publishing stays a staff action at ADMIN-02.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Deadline type is `date_specific` | Date picker visible and required |
| Deadline type is any other value | Date picker hidden |
| Any role's needed or interested value changes | Remaining recomputes and re-renders live, without saving |
| Status changes to `pending` | Submission emails queue on save |
| Request has no roles | Status selector does not offer `pending` |

## 9. Empty states

A request with no roles, reachable if a member left MP-11 before adding any. Renders the empty-state message in section 8: "No roles added yet."

## 10. Mobile differences

Closed per D60. Single column, same fields in the same order, full-width controls.

## 11. Authorization

Resolve the session's active memberships and confirm one matches `volunteer_requests.org_id` for `:id`, server-side, before any read or write. A member of another organization gets the same response as a request that does not exist.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Needed quantity lowered below interested | Blocked, naming the role |
| Save transaction fails partway | Nothing written, every entered value retained |
| Concurrent edit by another member | Last write wins (D8). Same policy as MP-09 |
| Status change to `pending` with no roles | Blocked |
| `:id` does not resolve | Same response as unauthorized |

## 13. Out of scope for this surface

- Approving a request or setting it to `active`. ADMIN-02.
- Writing `quantity_interested` by any path.
- Deleting a role or a request. **Closed per D7** (`DECISIONS.md`): roles cannot be removed on either edit surface; only added or their editable fields changed. Requests archive; roles cannot be removed.
- Setting `expires_on`.

## 14. Acceptance

- Editing and saving persists every changed field across the request and all its roles.
- `quantity_interested` cannot be changed from this surface by any means, including a tampered payload.
- `quantity_confirmed` can be changed and does not affect public availability.
- Remaining recomputes live and always equals needed minus interested, floored at zero.
- Lowering needed below interested is blocked with a message naming the role.
- The status selector never offers `active` to a member.
- A status change writes exactly one `approval_events` row. A save with no status change writes none.
- Moving to `pending` queues both submission emails once.
- A member of another organization cannot load the surface.
- Field order, labels, and copy match the desktop screenshot. Mobile matches the mobile screenshot.
