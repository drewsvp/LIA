## 1. Purpose

The public list of volunteer opportunities. Structurally parallel to PB-01, with one extra searchable field and a smaller list.

**Population display policy (D61):** The "Select 1-2" constraint is confirmed specific to MP-03's signup form only. Live organization profiles show anywhere from three to eleven populations selected. MP-05's edit checklist carries no cap; build it uncapped. This browse surface does not show populations on cards.

## 2. Entry and exit

**Arrives from:** the site navigation, social and email links, the legacy hub redirect, and PB-04 via back navigation.
**Leaves to:** PB-04 `/volunteer/:id`, by selecting a request card.

An unmatched legacy volunteer identifier lands here rather than on a 404.

## 3. Data

**Reads:** `volunteer_requests` where `status = 'active'`, joined to `organizations` where `kind = 'member_org'` and `status = 'approved'`. Fields: title, description, image, event location, and the organization's name, city, and available logo.

**Writes:** Nothing.
**Functions called:** None.

**Never returns:** contact people, emails, phones, signup data, non-active requests, or unapproved organizations. Same shared public query helper as PB-01.

## 4. Layout regions

1. **Page heading and introductory copy.** Confirmed order: hero heading,
   then two lines of introductory copy, then a bolded search-instruction
   line, directly above the search box.
2. **Search region.** Single text input, no visible filter controls
   beyond it.
3. **Request list.** Grid, three columns at desktop width, no visible
   pagination or load-more control across eleven results. Given ~24 total
   volunteer requests per the migration audit, default to an unpaginated
   full list unless the live site proves otherwise at higher volume.
4. No page-level "pagination or load more" element observed.

Captured from PB-03-desktop.png, Aug 16 2026. Matches PB-01's presumed
structure; confirm PB-01 independently rather than assuming from this.

### Card contents

Confirmed order, top to bottom: square photo with a small circular organization
icon overlaid at its top-left when available; title, bold caps; "Requesting
Organization" (underlined label) plus org name; "Location" (underlined
label) plus value; "Description" (underlined label) plus truncated text
ending in an ellipsis; button, "Learn More / View Roles."

**Two location values exist on this side, resolved: the card shows
`event_location`.** Confirmed against all eleven visible cards, values
range from a single word ("Hybrid") to full street addresses to
multi-city lists, consistent with a free-text per-request field, not a
resolved organization city. No prefix precedes the value beyond the
"Location" label itself.

Card tokens in `Design.md`. The confirmed shadow was measured against twelve cards on this page specifically.

## 6. Actions

**Card selection**
- Navigates to PB-04 for that request. No write.

**Search input**
- Filters as the visitor types, debounced.
- Searches: request title, organization name, event location, and organization city. Four fields, one more than PB-01.
- **Debounce interval, closed: 300ms.** Standard value, applied to both
  PB-01 and PB-03 identically.
- **Sort order, closed: most-recent-first.** Matches the confirmed pattern on both MP-13 tables, the one place with direct sort-order evidence from this site.
- No write, no navigation, no reload.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Visitor types in search | List filters after the debounce interval |
| Search matches nothing | Empty state per section 9 |
| Search cleared | Full list returns |
| A request has no image | Standard square placeholder graphic, consistent with how the org icon/photo pattern degrades elsewhere on the site |
| A request's organization has no logo | No circular logo overlay is rendered |
| A request has no event location | Hide the field rather than showing it blank. Matches deviation three (PB-02's dropoff-location finding is the exception, not the rule) |

## 9. Empty states

Two, captured independently: no active volunteer requests at all, and search matched nothing.

The first is a live possibility here in a way it is not on PB-01. There are far fewer volunteer requests than item requests, so an empty list is a state a real visitor will hit. Copy in section 8.

## 10. Mobile differences

Closed per D60. Single column, same fields in the same order, full-width controls.

## 11. Authorization

None to view. As with PB-01, the work is confirming nothing beyond section 3 is serialized into the response. Check the payload, not the page.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Request query fails | A stated error. Never an empty list |
| A request's organization does not resolve | Exclude and log. No card with a missing organization name |

## 13. Out of scope for this surface

- Any signup action. That is PB-04.
- Filtering by population, date, or commitment level.
- Sorting controls.
- Counts or totals.

## 14. Acceptance

- Only `active` volunteer requests belonging to `approved` `member_org` organizations appear.
- Each card shows a square request image (or square placeholder), the available organization logo in a circular top-left overlay, the correct organization's name, and the captured location value.
- Search filters on all four fields and is case-insensitive.
- Debounce matches the captured interval.
- Both empty states render with their captured text.
- The response payload contains no contact or signup data.
- A failed query renders a stated error, not an empty list.
- Card shadow and radius match `Design.md`.
- Desktop and mobile match their screenshots.
