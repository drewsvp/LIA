## 1. Purpose

The entry point for organization members. A member arrives here, enters their email, requests a magic link, and is routed to their organization's dashboard after authentication. The surface holds a heading, instructional copy, one email field, and one submit control.

## 2. Entry and exit

**Arrives from:**
- The site navigation link that members use to reach the portal.
- Redirect from any authenticated route when no session exists.
- Legacy redirect from the old dashboard entry path.

**Leaves to:** MP-02 resolves the destination after successful authentication. This surface does not decide where the member goes. See MP-02 section 2.

**MP-01C, the confirmation step (`/login/verify`).** The emailed link no longer completes sign-in on arrival. It lands on a confirmation surface that consumes nothing; a single "Sign in" button POSTs, and only that POST establishes the session. See D66 — mail-security scanners and link prefetchers were following the URL and spending the token before the member clicked.

An already-authenticated visitor who reaches `/login` is routed onward by MP-02 rather than being shown the login form again.

## 3. Data

**Reads:** `users`, `people` (via the auth layer only).
**Writes:** `users.last_login_at`. Session records, owned by the auth layer.
**Functions called:** None.
**Never touches:** `org_memberships`. This surface authenticates; it does not authorize. Membership resolution belongs to MP-02.

## 5. Fields

| # | Label (verbatim) | Control | Required | Binds to | Validation |
|---|---|---|---|---|---|
| 1 | Email* | Email | Yes | Auth layer email lookup | Valid email format |

The asterisk is part of the label with no space before it, matching the live capture exactly. Do not harmonize toward PB-02's "Email *" with a space; that spacing inconsistency exists on the live site and this surface preserves it.

**Login method: magic link (D40, confirmed Aug 14).** The password field from the legacy surface does not carry over; magic link replaces it. Tiffany reviewed the reasoning and did not object.

## 6. Actions

**Send Login Link**
- Enabled when: always.
- Does: sends a magic-link email to the entered address via the auth layer.
- Transaction boundary: none.
- Emails queued: one magic-link email.
- On success: the sent-confirmation state in section 8 renders in place of the form.
- On failure: the authentication flow renders its own failure state. Do not build a second error surface here.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Visitor already has a valid session | Routed per MP-02, login form not shown |
| Magic link sent successfully | Sent-confirmation copy replaces the form |
| Magic link opened (GET) | MP-01C confirmation surface renders; nothing is consumed |
| Same link opened repeatedly inside its 15-minute window | Still valid; each confirmation returns a session (D66) |
| A newer link was requested for the same email | The older link is refused as superseded |
| Authentication succeeds via the link | `users.last_login_at` set, control passes to MP-02 |

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Authentication rejected | The auth layer's failure state. The message must not reveal whether the email exists in the system |
| Magic link expired | MP-01C states the link expired and offers "Request a New Link", which returns to the email entry screen. Never a dead end |
| Magic link superseded by a newer one | MP-01C says a newer link was sent and offers the same recovery button |
| Magic link token missing or unrecognized | Same recovery path. The wording is identical for an unknown token and a swept one, so it discloses nothing about registration |
| Authenticated user has zero active memberships | Handled by MP-02, not here |

## 13. Out of scope for this surface

- Organization registration. That is MP-03.
- Any membership or permission check.
- Password reset flows beyond what the auth layer provides.

## 14. Acceptance

- The login form is visible and legible. Specifically, it is not white text on a white background; see the known bug in `Design.md`.
- Opening the emailed link does not sign the member in and does not consume the token; the confirmation button does.
- A link that has been fetched by a scanner still works when the member clicks it.
- Authenticating routes the member onward without a second click beyond the confirmation button.
- An authenticated visitor hitting `/login` directly does not see the login form.
- A failed attempt does not disclose whether the email is registered.
- Desktop and mobile match their screenshots.
