## 1. Purpose

Where a member changes an existing item request and the items on it. Request-level fields, every item's editable fields, and the ability to add further items all live here.

**This surface is three independently-submitted forms on one page, not one form**, matching its own instructional copy ("Use each part of the form separately"). Request-info fields, the items list, and the add-item form each have their own submit action.

**Two deviations from the current surface, settled.** Claimed counts are display only (D1, deviation six) and the status selector never offers `active` to a member (D2, deviation seven). Both are described in section 5 and section 6.

## 2. Entry and exit

**Arrives from:** MP-04, by selecting an item request and activating its edit control.
**Leaves to:** MP-04 via the back control.

Items are added inline on this surface via the "ADD ITEMS TO THIS REQUEST" form (region 4). No separate link to MP-08 exists and none is needed — add-item functionality is native to this page.

**Reads:** `item_requests` for `:id`, `items` for that request, `organizations.name`.

**Writes:** `item_requests` request-level fields. `items` editable fields, and new `items` rows. `approval_events`, when and only when status changes.

**Functions called:** None.

**Never touches:** `items.quantity_claimed`. See the conflict in section 5. `items.quantity_remaining`, which is generated. `approved_at`, `approved_by`.

### Conflict 1: claimed quantity is editable on the current surface

The surface being replaced allows a member to type over the claimed quantity. `Handbook.md` invariant 2 says `quantity_claimed` is written by `record_item_pledge()` and by nothing else, ever. These cannot both hold.

An editable claimed quantity means a member can silently desynchronize the counter from the pledge lines that back it, which makes the drift check fail, makes the public remaining count wrong, and makes it impossible to tell whether a donor's claim was recorded.

**Specified behavior: claimed is display only (D1).** `quantity_received` remains editable on an Active request, because that is the organization's own record of what physically arrived and it is not a public claim counter. The save locks the request before its item rows and rechecks Active before changing a received value. This prevents a stale member save from adding activity after staff has unapproved the request for correction. Deviation six in `Handbook.md` section 4.2. It is invisible in layout, since the field stays on screen, and visible only in that one input becomes a read-only value.

If a member needs to correct a claimed quantity, that is a staff action, and there is no admin surface for it this week. Note it for phase two rather than building a back door.

### Conflict 2: reducing requested quantity below claimed

Lowering `quantity_requested` below the existing `quantity_claimed` produces an item that is over-claimed. `quantity_remaining` is generated with a `greatest(..., 0)` floor so it will not go negative, but the item is now in a state where more is promised than is wanted.

**Specified behavior:** block the save with a stated message naming the item and its claimed count. Exact wording written fresh at build time.

## 6. Actions

Three independent submit actions, one per form region. Saving one region does not require saving the others.

**Submit Request Edits** (request-info region)
- Enabled when: request-info fields pass validation.
- Does: saves request-level fields only. Writes an `approval_events` row if and only if status changed.
- Transaction boundary: request-level fields only.
- Emails queued: submission emails when status moves to `pending`.
- On success: success message for this region.
- On failure: failure message, nothing written for this region, values retained.

**Submit Item Edits** (items-list region)
- Enabled when: at least one item is present and item fields pass validation.
- Does: saves every item's editable fields in one transaction.
- Transaction boundary: all item changes succeed together or none do.
- Emails queued: none.
- On success: success message, list re-renders with recomputed remaining.
- On failure: failure message, nothing written, every entered value retained.

**Add This Item** (inline form, per MP-08)
- Enabled when: the add-item form passes validation.
- Does: inserts one `items` row with `quantity_claimed` and `quantity_received` at zero and the next `sort_order`. Writes immediately on submit.
- Transaction boundary: single insert.
- Emails queued: none.
- On success: item appears in the list, form clears.
- On failure: form retains values, error renders, nothing inserted.

**Back control**
- Navigates to MP-04. No write.

### Conflict 3: the status selector

The current surface offers a status selector including the value that makes a request public. `Handbook.md` section 12 puts that transition at ADMIN-02, staff only, and section 6 requires every transition to write an approval event. A member who can set their own request to `active` has bypassed approval entirely, which is the governance property the rebuild exists to establish.

**Specified behavior: the selector stays, its options narrow.** A member may move their request:

| From | To | Meaning |
|---|---|---|
| `draft` | `pending` | Submit for approval. Queues `staff_new_item_request` and `org_request_received`, same as MP-08 |
| `active` | `archived` | Close a request that is no longer needed. `archived_reason = 'manual'` |
| `archived` | `pending` | Reopen, returning through approval rather than straight to public |

A member may never set `active`. That option does not render for a member.

This is deviation seven (D2). Status option labels are contextual on current status, inferred from D2 rather than directly observed — correct if the live dropdown shows otherwise:

| Current status | Options offered to member |
|---|---|
| `draft` | Pending (submit for approval) |
| `active` | Archived |
| `archived` | Pending (reopen for re-approval) |

`active` is never offered directly; publishing stays a staff action at ADMIN-02.

## 9. Empty states

A request with no items, reachable if a member left MP-08 before adding any. Renders the empty-state message in section 8: "No items added yet."

## 10. Mobile differences

Closed per D60. Single column, same fields in the same order, full-width controls.

## 11. Authorization

Resolve the session's active memberships and confirm one matches `item_requests.org_id` for `:id`, server-side, before any read or write. A member of another organization gets the same response as a request that does not exist.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Requested quantity lowered below claimed | Blocked, naming the item |
| Save transaction fails partway | Nothing written. Every entered value retained |
| Another member edited the same request concurrently | Last write wins (D8). No conflict UI this week |
| Received quantity save races staff unapproval | Exactly one commits. If unapproval wins, the stale received change returns a conflict and nothing in the item form is saved |
| Status change to `pending` on a request with no items | Blocked |
| `:id` does not resolve | Same response as unauthorized |

## 13. Out of scope for this surface

- Approving a request or setting it to `active`. ADMIN-02.
- Writing `quantity_claimed` by any path.
- Deleting an item or a request. **Closed per D7** (`DECISIONS.md`): items cannot be removed on either edit surface; only added or their editable fields changed. Requests archive; items cannot be removed.
- Setting `expires_on`.

## 14. Acceptance

- Editing and saving persists every changed field across the request and all its items.
- `quantity_claimed` cannot be changed from this surface by any means, including a tampered request payload.
- `quantity_received` can be changed and does not affect public availability.
- Remaining recomputes live while editing and always equals requested minus claimed, floored at zero.
- Lowering requested below claimed is blocked with a message naming the item.
- The status selector never offers `active` to a member.
- A status change writes exactly one `approval_events` row. A save with no status change writes none.
- Moving to `pending` queues both submission emails once.
- A failed save writes nothing and loses nothing typed.
- A member of another organization cannot load the surface.
- Field order, labels, and copy match the desktop screenshot. Mobile matches the mobile screenshot.
