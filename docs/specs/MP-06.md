## 1. Purpose

Where an existing member invites another person at their organization to get access. The invitation creates a person, a user, and a membership at `pending`, and notifies staff. The invited person gets nothing until staff approve at ADMIN-03.

This is the surface where the fault class from `Handbook.md` section 16, row one, used to originate. Every write here is in one transaction, names follow section 8, and one identifier resolves the person. If any of those three change, the fault comes back.

## 2. Entry and exit

**Arrives from:** MP-04.
**Leaves to:** MP-04 via the back control. On successful submit the surface stays put, the form resets, and a success message renders, so a member can invite several people in a row.

## 3. Data

**Reads:** `organizations.name` for the session organization, to display.

**Writes, in one transaction:**
- `people`, or resolves an existing row by `lower(email)`
- `users`, linked to that person, at `status = 'invited'`, if one does not exist
- `org_memberships`, `role = 'member'`, `status = 'pending'`, `invited_by` set to the acting user
- `email_log`, for the staff notification

**Functions called:** None.

**Never touches:** `org_memberships.approved_at` or `approved_by`. Approval is ADMIN-03's.

No `approval_events` row is written here. The membership is created at `pending`; it has not transitioned from anything. The first event on this membership is written when staff approve it.

## 4. Layout regions

Confirmed order: page heading, instructional copy, "NEW CONTACT INFO" section heading, organization name (read-only), first name, last name, email, phone, submit button, back control above the heading.

## 5. Fields

| # | Label (verbatim) | Control | Required | Binds to | Validation |
|---|---|---|---|---|---|
| 1 | First Name | Text | Yes | `people.first_name` | Non-empty |
| 2 | Last Name | Text | Yes | `people.last_name` | Non-empty |
| 3 | Email | Email | Yes | `people.email` | Valid email |
| 4 | Phone Number | Text | Yes | `people.phone` | Confirmed required, matches every other contact form in the app |
| 5 | Organization Name | Read-only text | n/a | `organizations.name`, session | Not editable |

Field 5 is display only. It is populated from the session, never from user input, and its value is never trusted on submit. The organization for the new membership comes from the session server-side.

**Two name inputs, two columns, per `Handbook.md` section 8.** Never concatenate.

## 6. Actions

**Submit for Approval**
- Enabled when: all required fields pass validation.
- Does: the full write in section 3, as one transaction.
- Transaction boundary: every write succeeds or none do. A person created with no membership, or a staff notification sent for a membership that was never written, are both the original fault.
- Emails queued: `staff_new_user` to both staff addresses, linking to ADMIN-03. No email to the invited person at this stage; they hear nothing until approval.
- On success: form resets, success message renders, the member stays on the surface.
- On failure: nothing written, form retains its values, failure message renders.

**Back control**
- Navigates to MP-04. No write.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Email matches an existing person | Attach the existing person. See section 12 |
| Email matches a person who already holds a membership in this organization | Blocked. See section 12 |
| Submit succeeds | Form clears, success message renders |

## 10. Mobile differences

Closed per D60. Single column, same fields in the same order, full-width controls.

## 11. Authorization

Verify the session user holds an active membership in an organization, server-side. The new membership is created against the session's organization. The organization is never taken from field 5, a URL parameter, or any client-supplied value.

**Any active member may invite (D5).** Staff approval at ADMIN-03 is the control that makes this safe.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Email belongs to an existing person | Not an error. Attach the existing `people` row, create a user if one does not exist, create the membership. One human, one row |
| The person already holds an `active` or `pending` membership in this organization | Blocked, with the duplicate membership message in section 8. Do not create a second membership; the unique constraint on `(org_id, user_id)` will reject it anyway, so handle it before the database does |
| The person holds a `removed` membership in this organization | Reactivate by setting that membership back to `pending` rather than inserting a new row. The unique constraint requires this |
| Single-word name entered in either name field | Succeeds. Both fields are stored as entered, no parsing |
| Transaction fails partway | Nothing written. Every value retained |
| Staff notification fails to dispatch | The invitation stands. Logged as failed in `email_log`, surfaced in ADMIN-06. The inviting member sees success, because their action succeeded. Staff will find the pending membership in ADMIN-03 regardless of whether the email arrived |

The last row is why ADMIN-03 is a queue rather than an inbox-driven process. Approvals do not depend on an email arriving.

## 13. Out of scope for this surface

- Approving the membership. ADMIN-03.
- Sending login information to the invited person. That fires on approval.
- Setting a role other than `member`.
- Removing a member. MP-05.

## 14. Acceptance

- A complete submission creates exactly one membership at `pending` and one staff notification.
- Submitting an email that already exists in `people` creates no duplicate person.
- Inviting someone who already holds an active or pending membership is blocked with a readable message.
- Inviting someone whose membership was previously removed reactivates it to `pending`.
- A single-word name in either field succeeds.
- The invited person receives no email until staff approve.
- The organization name field is display only and its value cannot influence which organization the membership is created against. Verify by tampering with it.
- The form resets on success and the member stays on the surface.
- Field order, labels, and messages match the desktop screenshot. Mobile matches the mobile screenshot.
