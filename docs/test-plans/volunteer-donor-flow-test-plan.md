# Volunteer / Donor Flow Test Plan

**Package files:** this guide and `volunteer-donor-flow-test-cases.csv`  
**Audience:** staff testers running the public donor/volunteer and organization follow-through checks  
**Scope:** PB-02 item claims, PB-04 volunteer interest, MP-13 supporter visibility, optional supporter profile and digest opt-ins, related email records, safety, and concurrency.  
**Test data rule:** use synthetic fixtures only. Do not enter real names, contact details, credentials, or delivery addresses in screenshots, email evidence, or the CSV.

## 1. How to run this plan

1. Start from a non-production environment with staff-approved synthetic organizations and active synthetic requests. Use a private/incognito browser profile for each public visitor and separate authenticated browser profiles for Organization A, Organization B, and staff/admin.
2. Copy `volunteer-donor-flow-test-cases.csv` before a run. Complete `Result` with **Pass**, **Fail**, **Blocked**, or **Not Run**, and use `Notes` for the observed message, fixture identifier, defect link, or retest detail.
3. For every case, capture the evidence listed in the case: a redacted screenshot, relevant route/response status, redacted email/log record, and/or database/query result. Store evidence outside this document using the case ID in its filename.
4. Run public desktop checks at the supported desktop size and repeat the stated responsive cases at a narrow mobile viewport. Compare field order, labels, copy, conditional behavior, empty states, and full-width controls side by side with the approved captures where they exist.
5. Never use a production inbox or a real person for a test. Suggested synthetic identities are `zz.fixture.donor.one@example.test`, `zz.fixture.donor.two@example.test`, and `zz.fixture.volunteer@example.test`. The `.test` domain is intentionally non-deliverable; use the approved test-mail capture or staging inbox for email evidence.

## 2. Required deliberate concurrency setup

The final-item and final-role tests are not ordinary double-click tests. For **DC-06** and **VI-05**, give two testers separate browsers, separate synthetic emails, and identical completed forms against the one-unit/one-place fixture. Count down and submit together. The required result is exactly **one success and one handled failure**:

- final item: one success and one `insufficient_quantity` experience that identifies the affected item, preserves entered values, and shows refreshed availability;
- final role: one success and one `role_full` experience that identifies the affected role, preserves entered values including notes, and shows refreshed availability;
- after each race, query `counter_drift`; it must return **zero rows**. Do not repeat against the same final fixture after it has been consumed—reset it first.

## 3. Evidence and result rules

- Redact contact values in any screenshot or exported log. Keep only synthetic fixture identifiers where identification is needed.
- “Email succeeds” means the corresponding email is captured in HTML and plain text, has resolved variables and correct entity links, reaches the test inbox, and writes exactly one `email_log` row per recipient at `sent`.
- A successful public pledge/signup is still a success if later email dispatch fails; the failure must instead be visible as a readable `failed` email-log row.
- A stated error is not an empty state. In the staff supporter lists, test one branch at a time: a failed donor query must not hide a ready volunteer table, and vice versa.
- For route-access checks, record route/method, anonymous status, Organization B status, and whether any data or mutation occurred. Do not record response bodies containing personal data.
