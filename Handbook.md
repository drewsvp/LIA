## 1. What this system does

The Alliance is a nonprofit backbone organization serving the greater Sacramento region. It does not deliver services directly. It coordinates a network of roughly 105 member organizations, including foster and adoption agencies, nonprofits, churches, and professional service providers, all of which work with vulnerable children and families.

This application is the marketplace connecting those organizations' needs to the public's willingness to meet them.

A member organization posts a need: eleven twin mattresses for families exiting emergency shelter, a wheelchair for an elderly refugee, volunteers to coach a refugee youth soccer team. The public browses those needs, claims specific items in specific quantities, or expresses interest in specific volunteer roles. Alliance staff approve organizations, members, and requests before anything reaches the public.

**The people served by these needs are never named in this system.** Organizations post on behalf of families whose identities stay private. There is no recipient record, no beneficiary table, and no plan for one. Do not add one.

**Stakes.** This system is live and in use by real organizations meeting real material needs. Data loss is unacceptable. Silent failure is worse than loud failure. When a write cannot complete, fail visibly and tell the user. Never report success for an operation that did not happen.

## 3. Whose experience wins

Applies whenever two reasonable choices conflict and no rule settles it.

**The member organization is the client.** The Alliance's hundred-plus members are who this exists for, and who Christina supports daily.

**The public donor or volunteer is the user whose friction costs a filled need.** Every point of friction on a public surface is a need that does not get met.

**The family being served is the beneficiary and never appears in the system.**

So the tiebreaker runs by surface. On the member portal and the staff admin, the organization and the operator win. On the public flows, the donor or volunteer wins. Where they genuinely conflict, ask which choice results in more needs actually met; that is the closest available proxy for the beneficiary who is not in the database.

This is why the counter decisions went the way they did. An organization that cannot trust its remaining count stops trusting the system, and a donor who claims an item that was already gone does not come back.

## 4. The keep-it-the-same constraint

**Nineteen surfaces are bound.** They must look and behave the way the current system does. A member organization that logs in on August 25 should notice nothing except that things stopped breaking.

This binds the org member portal and both public flows. It does **not** bind the database, the staff admin, or anything a member never sees.

**"The same" means recognizable, not bug-for-bug.** We do not reproduce known defects. The deviation list in 4.2 is closed.

**"The same" means the flow and the layout, not the pixels.** Fonts render slightly differently and spacing lands within a few pixels. What must be identical: the same pages in the same order, the same fields in the same sequence with the same labels, the same buttons in the same places doing the same things, the same messages in the same words. If a member has to think about where something moved, we got it wrong.

Every bound surface has a desktop screenshot and a mobile screenshot. Mobile is a separate layout, not a breakpoint. Build both.

### 4.1 Surfaces that change behind the glass

**MP-02, login redirect.** Previously a string match on a text custom field, where a capitalization mismatch sent the member nowhere. Now a query on active `org_memberships`.

**MP-03, organization sign-up.** Names now stored as two columns. The form keeps both inputs exactly as they are.

**MP-05, member removal.** Previously deleted the member account, destroying history. Now sets the membership to `removed`. The screen behaves identically.

**MP-06, add a database user.** Now creates a person, a user, and a pending membership in one transaction. Same form, same fields, same success message.

**PB-02 and PB-04, the submit path.** Both call the counter functions. No page code touches quantity columns. Visible result identical, including auto-archive when an item request becomes fully claimed.

**MP-13, supporters view.** Reads from the pledge and signup tables. Same two tables, same summary strings.

### 4.2 Deliberate deviations, closed list

Eight changes to bound surfaces. Nothing else changes. All eight are settled; see `DECISIONS.md`.

1. **Volunteer requests gain a deadline date field.** The control is lifted verbatim from the item form. (MP-10, MP-12)
2. **The org-mission bug is not reproduced.** Mission resolves through a foreign key. Spot-check during testing; it is a visible win worth showing Friday. (PB-02, PB-04)
3. **Blank organization fields are not reproduced.** A field with no value is hidden, not rendered empty. (PB-02, PB-04)
4. **Auto-expiry covers volunteer requests too.**
5. **Approval emails resolve names and fields correctly.**
6. **Claimed and interested counts become display only on the edit surfaces.** They are counter columns written by the functions alone. Received and confirmed stay fully editable, because those are the organization's own record of what arrived and who served, and are not counters. (MP-09, MP-12)
7. **The status selector never offers `active` to a member.** Members may submit for approval, archive an active request, and reopen an archived one back into approval. 8. **Every form that captures a human's name uses two inputs, first and last.** This is the person identity and name policy in section 8, applied to bound surfaces. It affects the public claim and signup forms and any portal form that currently uses a single combined input. If capture shows a form already uses two inputs, nothing changes on that form.

## 6. Stack and conventions

**Runtime:** Node, TypeScript, built and deployed on Replit.
**Database:** Replit-managed Postgres (Helium), development and production (D58).
**Auth:** Better Auth, self-hosted in the Postgres database, so user and session data lives in the Postgres we own. Permission checks are enforced in route guards and the data-access layer. Fallback if the auth lane stalls past Tuesday: Clerk. Not Replit Auth.
**Login method:** Magic link (D40, confirmed Aug 14). Tiffany reviewed the reasoning and did not object.
**Email:** Resend. SPF, DKIM, and DMARC required on the sending domain.
**Repo:** mirrored to a GitHub organization owned by The Alliance.

`users.auth_subject` holds the provider's stable subject identifier and nothing else knows the provider, so swapping touches one column and one middleware file.

### Rules

- TypeScript strict mode. No `any` in committed code.
- All database access through a single data-access layer. No SQL in route handlers or components.
- Migrations are numbered, immutable once applied, and applied in filename order by the tracked runner (`server/db/apply-migrations.ts`, `npm run db:apply-migrations`) with sha256 checksum bookkeeping in `schema_migrations`. `0001` is never edited after application. Generate `schema.sql` after applying: `pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges > schema.sql`. Commit it. Never hand-edit it.
- Environment variables for all secrets, including in comments and test fixtures.
- Every image read and write goes through a single storage adapter module (D39). Replit object storage for the sprint; moving to S3-compatible storage after the sprint is then one file plus a copy job.
- Every mutation validates server-side. Client-side validation is a convenience, never a control.
- Timestamps stored UTC as `timestamptz`, rendered America/Los_Angeles.
- No currency anywhere. Do not add price fields.

### Authorization

Every route that reads or writes organization-scoped data checks membership server-side, on every request, before the query. Never derive authorization from a URL parameter, a client-supplied org ID, or a hidden form field.

Public routes expose only active requests belonging to approved member organizations, and the subset of organization fields needed to display a request: name, mission, website, city, logo, populations served.

No endpoint returns a person's email, phone, or supporter history to an unauthenticated caller. No endpoint returns another organization's supporter list to a member. **Check the response payload, not the rendered page**; a surface that renders correctly can still serialize contact details a visitor never sees but can read.

### Naming

Database snake_case, plural tables. TypeScript camelCase values, PascalCase types. Routes lowercase, hyphenated. Surface IDs in branch names, commit messages, and spec filenames.

## 7. Data model

Full definitions in `schema.sql`. Seventeen tables.

**Identity.** `people` is one row per human, permanently, holding name, email, phone. Email is the unique key, case-insensitive. Roles are relationships in other tables. Carries `needs_review`, `review_note`, `source_note`. `users` is authentication only, one-to-one optional with `people`, holding no permissions.

**Organizations.** `organizations` holds member organizations and the platform owner, distinguished by `kind`. Address as components plus a formatted string. `city` must be populated for every approved organization. `slug` is stable, human-readable, unique, and permanent. `org_memberships` is the only mechanism associating a person with an organization. `populations` and `organization_populations` are many-to-many, with `populations_other` holding free text.

**Requests.** `item_requests` and `volunteer_requests` are parallel. `items` and `volunteer_roles` hold the children, each with a generated remaining.

**Supporters.** `item_pledges` with `item_pledge_lines`, `volunteer_signups` with `volunteer_signup_roles`. A person who both donates and volunteers is one `people` row with rows in both branches.

**Governance.** `approval_events` records every status transition. `email_log` records every send attempt. `digest_subscribers` holds the weekly list.

### Invariants

Violating any of these is a defect.

1. **No text-matching joins.** A person resolves to an organization through `org_memberships` and nothing else.
2. **`quantity_claimed` and `quantity_interested` are written by `record_item_pledge()` and `record_volunteer_signup()` only.**
3. **`quantity_remaining` is generated.** Never written.
4. **Every status transition writes an `approval_events` row** in the same transaction as the status change, including automated ones.
5. **Every email send writes an `email_log` row** before dispatch, updated on result.
6. **`legacy_wix_id` is never a foreign key.**
7. **Deletion is not a workflow.** Members are removed by status, requests are archived. The single exception is the duplicate merge at ADMIN-04, which is staff-admin only, twice-confirmed, and audited.
8. **A person is identified by email and never by name.** No code path concatenates two name columns into one string or splits one string into two. See section 8.

### Two schema decisions made during spec writing

Both are in `migrations/0001_initial_schema.sql`. The merge's function, `merge_people()`, is created in `migrations/0003_merge_people_function.sql`.

**`approval_events.entity_type` accepts `person`.** The duplicate merge at ADMIN-04 is the only irreversible operation in the system and would otherwise leave no trace. Merge writes `from_status = 'duplicate'`, `to_status = 'merged'`.

**The email dedup index includes `to_email`.** Five templates send to more than one recipient for the same entity: the four staff notifications go to two addresses each, and `org_request_approved` goes to both the primary contact and the creator. Without `to_email` in the key the second row is rejected by the database and that person silently receives nothing. Semantics are once per recipient per entity, so approving twice still sends each person one email.

## 8. Person identity and name policy

App-wide. No surface, function, or migration step is exempt.

**A person is identified by email address.** `people.email` carries a unique index on `lower(email)`. No other column identifies a person, and no lookup resolves a person by name.

**Names are display data.** `people.first_name` and `people.last_name` are both `not null` and neither is unique. Every surface that captures a human's name captures two separate inputs and stores them exactly as entered. No surface concatenates the two into one string, and no code path splits a single string into two. This applies to public claim and signup forms, member portal forms, admin forms, and the migration, without exception.

**A person has exactly one email address.** A submission with a new email address creates a new person row. Consolidating two rows for the same human is the merge operation in ADMIN-04, not an automatic behavior.

**On public flows, a submission whose email matches an existing person updates that person's `first_name` and `last_name` to the values just submitted.** Name variance across submissions has no identity consequence.

**A person whose name changes keeps the same row and the same history.** Their `first_name` and `last_name` are updated in place.

**Before inserting a new person, public claim and signup flows check for an existing person with the same phone number.** On a match, the new person row is still created, with `needs_review = true` and a `review_note` naming the suspected duplicate. This is the only automatic duplicate signal in the system.

**Migration never guesses a name split.** A legacy name string that does not split confidently, including single-token names, hyphenated surnames, suffixes, and anything over two tokens, is imported with a best-effort split, the original string preserved in `source_note`, and `needs_review = true`. This applies to legacy Donor names and to every concatenated primary-contact name on Organizations, Item Requests, and Volunteer Requests.

**Mononymous people and non-personal contact values** are imported with both name columns populated and `needs_review = true`. The `not null` constraint is not relaxed.

**Out of scope for this build:** multiple email addresses per person, automatic merging, and name-similarity matching.

## 9. Status lifecycles

**Organizations:** pending → approved → disabled. Only approved organizations appear publicly or can post.

**Memberships:** pending → active → removed. Only active memberships grant access.

**Requests, both types:** draft → pending → active → archived.

`draft` is created but not submitted, visible only to its own organization. `pending` is awaiting staff approval, not public. `active` is public. `archived` records `manual`, `expired`, or `fulfilled` in `archived_reason`.

Archiving is reversible by staff and the reversal writes an event like any other transition.

---

## 10. Scheduled jobs

**Nightly expiry, 12:15 AM Pacific.** Selects item requests and volunteer requests where `status = 'active'` and `expires_on < current_date`. Archives them with `archived_reason = 'expired'`, writing an `approval_events` row per request with a null actor. Both types. Batches of 50, paging until exhausted. Idempotent.

**Fulfillment archiving is not a job.** It happens inside `record_item_pledge()` when the final item reaches zero remaining.

**Volunteer requests do not auto-archive when every role fills.** Interest is not commitment, people who express interest do not always follow through, and an organization still wants to hear from someone after a role fills. The volunteer side archives manually or by expiry only. This asymmetry is deliberate.

### Routing rules

**Dashboard routes carry no organization identifier.** The session resolves the organization.

**Post-login routing, MP-02.** Query active memberships. Zero gives a pending-approval message and no dashboard access. One goes to `/dashboard`. More than one shows a chooser, then `/dashboard` scoped to the selection, which persists in the session with a visible switcher.

**Legacy request routes.** `/area-needs-request/:legacyId` and `/area-needs-volunteer-request/:legacyId` resolve on `legacy_wix_id` and 301 to the new path. Unmatched identifiers return the corresponding browse page, not a 404.

### Behavior common to multiple surfaces

**Deadline control** (MP-07, MP-09, MP-10, MP-12). Type selector; date picker visible and required only for `date_specific`. One component.

**Submit gating** (MP-08, MP-11). Submit for approval disabled until at least one item or role exists. The same rule applies to the status selector on MP-09 and MP-12.

**Availability gating** (PB-02, PB-04). Quantity input disabled at zero remaining; role checkbox disabled at zero remaining. The disabled control is a courtesy; the function re-validates under a row lock regardless of what the client sends.

**Conditional product link** (PB-02). Renders only when the item has one.

**Search** (PB-01, PB-03). Filters as the user types, debounced. PB-01 searches request title, organization name, and city. PB-03 adds event location. Debounce interval in the specs.

**Supporter summary** (MP-13, and `org_new_item_donation`). Both contexts
resolve from the same `item_pledge_lines` query, so they never disagree
on *what* was pledged, but they render it differently, confirmed Aug 16
2026: MP-13 lists each item on its own line within the table cell
(`{quantity}x {item name}`, no separator), the email renders a table
instead (D51). **Strike the `3x Blankets, 2x Pillows` example**, it
described neither surface correctly. What's shared is the underlying
data and the query that produces it, not a single string format.

**Organization display fields.** Mission, website, logo, city, and populations render from the organization resolved through `org_id`. No other source. A field with no value is hidden.

**Concurrency failure** (PB-02, PB-04). The functions raise `insufficient_quantity` or `role_full` when two supporters claim the last unit at once. This is a real path on a popular request. The surface keeps every value the person entered, names the specific item or role that was taken, and re-renders current availability. Never a generic error, never a silent partial success.

**Failed query versus empty list.** A query that fails and renders as an empty list tells an organization its requests are gone, or tells a donor there are no needs. Every list surface renders a stated error instead.

## 12. Approval workflows

Three workflows. All transition status, write an approval event, and queue email in one transaction.

**Organization approval.** Sign-up creates the organization at pending, a person for the primary contact, a user, and an owner membership at pending. Staff approve at ADMIN-01: the organization becomes approved, **the owner membership becomes active in the same transaction**, and the primary contact receives the welcome email. Owner memberships never appear in the ADMIN-03 queue.

**Request approval.** A member creates at draft, adds items or roles, and submits to pending. Staff receive notification; the submitter receives a confirmation. Staff approve at ADMIN-02: status becomes active and the request appears publicly. The primary contact and the creator both receive the approval email; if they are the same person, once.

**Member approval.** An org member invites at MP-06. The system creates or finds the person, creates a user if needed, and creates a membership at pending. Staff approve at ADMIN-03.

Approval is idempotent. Approving an already-approved entity is a no-op that sends no email, not an error.

## 13. Email

Twelve templates. Subjects, variables, and shared rules in `docs/email/TEMPLATES.md`.

All sends write `email_log` before dispatch and update on result. Deduplication is once per recipient per entity, per the index decision in section 7.

Staff notifications go to two addresses, a primary staff contact and a general information address, both from environment variables.

**Every variable resolves before send.** A template that would render an empty name, an empty organization, or a literal placeholder does not send: log it failed with the reason and surface it at ADMIN-06. This is the direct fix for the blank-name failure in section 16.

## 14. Migration

Field mappings in `docs/migration/field-map.md`. That directory is the only place source-export structure is described.

**Two source exports, not one.** Six CMS collections cover organizations, requests, items, roles, and supporters. **The digest subscriber list and the member-approval label live in the contacts system**, which is a separate export and the only way to reconstruct which members are currently approved.

**Expected volumes**, measured from the 2026-08-14 export. Organizations 49, item requests 120, items 403, volunteer requests 24, volunteer roles 58, supporter records 127. Total 781, plus subscribers.

**Imported after exclusions:** organizations 49 plus 1 platform owner, item requests 116, items 395, volunteer requests 24, volunteer roles 54, item pledges 83, volunteer signups 38, item pledge lines 173, people 160. Exclusions and reasons in `docs/migration/exclusions.csv`.

**Identity resolution** follows the person identity and name policy in section 8. People match on `lower(email)`, never on name. A name that does not split confidently is imported best-effort with the original string in `source_note` and `needs_review = true`.

**Counters are recomputed** from imported lines after load, never carried from the export.

**Populations** are seeded per D61: ten canonical MP-03 values plus Other, not from all 24 distinct export values.

**Slugs** are assigned during migration and are permanent.

**Media** is rehosted on Replit object storage for the sprint, behind the storage adapter in section 6 (D39). Source-hosted URLs are never written to the database (D38).

**No `approval_events` backfill.** The source records neither actor nor timestamp for approvals. An empty audit trail with a known start date is more honest than a fabricated one (D36).

**All active requests migrate as-is (D42).** No pre-migration outreach or cleanup pass.

**Migrated item and volunteer requests leave `approved_at` and `submitted_at` null on the one-time historical batch only (D43, D48).** They are not derived from any source field. That null default is not a general import rule. Live approvals at ADMIN-02 write `approved_at = now()`. The eventual digest job includes a request only when `approved_at` is both non-null and within the lookback window.

**Deliverables:** `redirects.csv`, `dropped-fields.csv`, `migration-exceptions.csv`, and a written validation report. The exceptions file records every place the import made a choice the source did not determine, which is what makes the result auditable rather than merely trusted.

**Validation** required before acceptance: exact row counts per table, full referential integrity, `counter_drift` returning zero rows, non-empty `city` on every approved organization, no duplicate emails, and every source record mapping to exactly one destination row by `legacy_wix_id`.

**Four field types are at risk:** per-item quantity arrays, multi-value references, structured addresses, and hosted image references. Test all four on a sample export before any full run.

**The migration is not a numbered migration.** `transform.py` reads the six CMS exports offline and writes one CSV per target table into `data/load/`, plus a generated `load.sql` that loads them with `\copy`. It runs once, against one database, from files that will not exist in six months. Keeping it out of `/migrations` is what keeps `0001` a statement of the architecture rather than a history of one nonprofit's data.

## 15. Build lanes

Everything depends on the data layer, so the data layer publishes its **contracts** Monday morning even though its implementation lands later.

**Lane 0, day one, blocking.** Migrations applied to the shared development database. Data-access layer signatures published, even as stubs. Route table scaffolded. Auth wiring. Seed script.

**The seed script is not test hygiene.** Until the migration runs, every other lane builds against an empty database. The seed creates the platform-owner organization, three approved member organizations, one pending, active item and volunteer requests with children at varying remaining counts including zero, a fully claimed request, and several pledges and signups. Without it nobody can see an empty state, a disabled input, or a full role, which is exactly the behavior the bound surfaces are judged on.

**Lane A, member portal.** MP-01 through MP-13. Largest lane, and the one Christina walks. Build in journey order.

**Lane B, public and email.** PB-00 through PB-05 plus the twelve templates. Demo material and highest traffic.

**Lane C, admin and migration.** ADMIN-01 through ADMIN-08 plus the migration and validation. Build the shared admin shell first.

**Shared contracts that must not drift:** the route table in section 11, the data-access signatures, the surface IDs, the `docs/Design.md` tokens, and the item summary format. Changes are captain calls, announced rather than committed quietly.

## 16. The five failures that must be provably absent

Each is addressed by a property of this design. Each also needs a test, because "we rebuilt it" is not evidence and the judging package asks for objective data.

| Failure | Design property | Test |
|---|---|---|
| **New user, no contact.** Creation and notification were separate; a name-parsing crash and an identifier confusion left users half-created. | One transactional creation path, names as separate columns, one identifier. | Invite a member at MP-06 with a single-word name and a three-part name. Each produces one `people` row, one `users` row, one pending membership, one staff email. |
| **Blank org website.** Org fields came through a free-typed name match. | Foreign key from request to organization; required fields enforced at the database. | Every active request page renders its own organization's mission, website, and city. Run across all migrated requests, not a sample. |
| **Stale dated requests.** Expiry covered one type. | One nightly job selecting from both tables. | Seed one item and one volunteer request with yesterday's `expires_on`. Run the job. Both archive, both write an event. |
| **Approval fails, blank name.** The contact might not exist, code read fields not guaranteed present, template variables were inconsistent. | Approval creates the person if needed, reads only defined columns, and an unresolved variable blocks the send. | Approve an organization whose contact has no prior record; the email sends with a resolved name. Then force an unresolved variable and confirm the send is blocked and logged failed at ADMIN-06. |
| **Public endpoints.** Member creation, deletion, lookup, and email were callable by anyone. | Membership checked server-side before every organization-scoped query; enforced in route guards and the data-access layer. | Enumerate every route. Call each unauthenticated and as a member of a different organization. No personal data, no other org's data, no mutation succeeds. Record the result as a table; it is presentation material. |

## 17. Out of scope

Do not build. Do not add columns, routes, or UI in anticipation.

- **Fulfillment tracking.** No status on pledges, no receipt step, no confirmation flow.
- **Reporting and impact dashboard.** No aggregate metrics, no charts, no counts on any surface. When this is built, its queries must not inherit the public-surface filter `organizations.status = 'approved'` (D14, D44). A disabled organization's historical needs-met count has to remain visible for annual reporting. `LIA_Phase_Two_Backlog.md` is not in this corpus; this is the parked note until that file exists.
- **Digest send job.** The table and the subscribe form are in scope; the send is not. ADMIN-08's CSV export exists so the list is usable in the meantime. No current spec owns the send logic (PB-05 is the subscribe form; ADMIN-08 is subscriber admin). When that spec is written, the eligibility rule is: a request is digest-eligible only when `approved_at` is both non-null and within the lookback window (D43). Historical migrated rows are left null; anything that becomes active afterward must get a real timestamp (D48). The Thursday demo does not send to the live subscriber list; real cutover is the following week (D46). If the send job is not built for Thursday, showing the digest manually is an acceptable outcome.
- **Public per-organization pages.** Slugs are assigned; no route consumes them.
- **Recipient records.** See section 1.
- **Anything not specified in this file.** If a task seems to require one, stop and ask.

The schema accommodates every one of these without structural change. That was the test each had to pass.

## 18. Definition of done

**Data.** Full migration against production with a passing validation report. Migration-sourced people review queue empty. `counter_drift` returns zero rows.

**Function.** Thirteen member portal surfaces built and matching screenshots, desktop and mobile. Five public surfaces likewise. Eight admin surfaces built and operable. Three approval workflows complete end to end, each writing an event. Twelve templates sending with correct variable resolution, verified against a live inbox, with one row per recipient. Nightly expiry scheduled and verified against both types. Legacy routes resolving. All five tests in section 16 passing, results recorded.

**Security.** No unauthenticated endpoint exposes personal data or another organization's data, verified against response payloads. Every organization-scoped route verifies membership server-side. No secrets in the repository. SPF, DKIM, DMARC verified.

**Handover.** Repository mirrored to the Alliance-owned GitHub organization. Environment variables documented. Migration and validation reports committed. `redirects.csv` delivered. **The program director completes the full member journey unassisted:** sign up, create an item request, add items, submit, edit, view supporters.

That last item is the acceptance test that matters most. Any point at which she has to ask what to do next is a defect, regardless of whether the surface matches its screenshot.
