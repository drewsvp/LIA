A marketplace connecting [The Alliance](https://thealliancerc.org)'s member organizations (Roseville, CA) to the public. Organizations post material and volunteer needs; the public claims items or expresses interest in roles. Alliance staff approve organizations, members, and requests before anything is public.

This repository is the **build contract, source assets, and migration pipeline** for the August 17–21, 2026 rebuild — an [SVP AI for Good Hackathon](https://www.socialventurepartners.org) project. Application code (Node/TypeScript on Replit) is not in this tree yet; everything needed to build and migrate the live Wix system is here.

**Start here:** [`Handbook.md`](Handbook.md) is the authoritative build contract. [`replit.md`](replit.md) is the agent rules file — read it first on every task. [`SPRINT.md`](SPRINT.md) coordinates the week for people, not agents.

## What this project is

The Alliance coordinates a network of roughly 105 member organizations serving vulnerable children and families across the greater Sacramento region. Love in Action (LIA) is their **Area Needs Database** — the system those organizations use to publish needs and the public uses to respond.

| Actor | What they do |
|---|---|
| **Public visitor** | Browse active requests, claim items, express volunteer interest, subscribe to the weekly digest |
| **Org member** | Create and edit their organization's requests, invite members, remove members |
| **Staff approver** | Approve organizations, members, and requests |
| **Staff admin** | Everything above, plus people review, populations, email log, audit trail, subscribers |

**Stakes:** This system is live and in use by real organizations meeting real material needs. Data loss is unacceptable. Silent failure is worse than loud failure.

**Privacy:** The people served by these needs are never named in this system. There is no recipient table and no plan for one.

## How this repo got build-ready

The original plan was a Monday-morning capture walkthrough: two hours, in person, working through all eighteen originally-bound surfaces against the live site with Tiffany and Christina. That walkthrough never happened. Instead, over one session the night before kickoff, every spec was closed directly against real screenshots of the live system as they came in, one surface at a time.

Two things came out of that besides filled-in copy. First, a public landing page, `PB-00`, turned out to have never had a spec at all despite being a real, bound, necessary surface, the root `/` route. It's specified now, from capture, same as everything else. Second, a handful of genuine current-system inconsistencies surfaced that no document had caught: the organization sign-up form and the organization-edit form showed two different, mismatched lists of population categories; a volunteer-request status control was labeled for item requests, a copy-paste leftover; a pagination control showed a stuck placeholder count instead of a real one. None of these were guessed at, each is recorded with its reasoning in `DECISIONS.md` (D58–D61), and one, the population taxonomy, was resolved by asking Christina directly rather than picking a default.

By the end of that pass, the corpus went from roughly 418 open placeholder markers across the specs to zero. What's genuinely still open isn't in the specs, it's the three items in "Current status" above that need something from Tiffany, not a document: the contacts export, the staff roster, and one email body.

## Stack

| Layer | Choice |
|---|---|
| Runtime | Node, TypeScript strict, deployed on Replit |
| Database | Replit-managed Postgres (Helium). Portable by driver choice, not by migration plan (D58). |
| Auth | Better Auth (self-hosted in Postgres), magic link login (D40) |
| Email | Resend with SPF/DKIM/DMARC |
| Storage | Replit object storage for sprint (single adapter module, D39) |

All database access goes through one data-access layer. Migrations are numbered SQL in `/migrations`. Timestamps stored UTC, rendered America/Los_Angeles.

## Migration pipeline

Legacy data lives in six Wix CMS collections. The transform is offline — no application code, no ORM — so a human can review CSVs before anything touches the database.

```bash
# Place six CMS exports in data/legacy-export/ (see data/README.md)
python3 transform.py --source data/legacy-export --out data/load

# Apply schema, then load (requires DATABASE_URL)
psql "$DATABASE_URL" -f migrations/0001_initial_schema.sql
psql "$DATABASE_URL" -f load.sql

# Validate
psql "$DATABASE_URL" -f docs/migration/validation.sql
```

**Rules:** `docs/migration/field-map.md` (contract). **Measurements:** `docs/migration/data-audit.md` (Aug 14 export).

The transform produces thirteen table CSVs plus `redirects.csv`, `migration-exceptions.csv`, and a transform report. It does **not** produce `users`, `org_memberships`, or `digest_subscribers` — those require the separate contacts export, which has not been received.

`data/legacy-export/` and `data/load/` are gitignored (PII). Do not commit them.

## Rules that are never broken

Eleven invariants from `replit.md`. Violating any is a defect.

1. No text-matching joins — people resolve to organizations through `org_memberships` only
2. `quantity_claimed` and `quantity_interested` written by database functions only
3. `quantity_remaining` is generated, never written
4. Every status transition writes an `approval_events` row in the same transaction
5. Every email send writes an `email_log` row before dispatch
6. `legacy_wix_id` is never a foreign key
7. Deletion is not a workflow — members removed by status, requests archived
8. Authorization is server-side on every request, before the query
9. No secrets in the repo
10. People served by needs are never named in this system
11. A person is identified by email, never by name — two inputs, two columns, stored as entered
